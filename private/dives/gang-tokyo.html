GANG TOKYO

A custom visual-novel / narrative-RPG engine where the engine is code and the game is JSON — built from scratch because Ren'Py fights you and Unity is a cannon for a fly.

STACK: .NET 8 + MonoGame (DesktopGL) TIMELINE: Jun 2026 → present ROLE: engine, content schema, everything
01 PLANNING 02 DEVELOPMENT 03 FEATURES 04 LESSONS 05 FUTURE
01

PLANNING

/ the brainstorm & the research
THE ITCH

"Every VN tool makes you write the story inside the engine. I wanted the opposite: a tiny C# core I fully own, and a game that's just data files I can diff, edit, and regenerate."

RESEARCH TRAIL
  • → Ren'Py teardown — great until you need a mechanic it doesn't have
  • → Unity dialogue assets — editor lock-in, 3 packages deep before "hello"
  • → Data-driven engine design — commands as data, interpreter as code
  • → MonoGame DesktopGL — the boring, stable, cross-platform choice

BRAIN DUMP #1

The engine is code. The game is JSON. You only touch C# for a brand-new kind of command.

BRAIN DUMP #2

Scenes, characters, items, activities, branching logic — all editable data files. Writers shouldn't need a compiler.

CONSTRAINTS

  • .NET 8 SDK is the only prerequisite. No content pipeline.
  • Small, ownable codebase — readable in one sitting.
  • Combat ships as a hook first; card battles are Phase 2.

DECISION! JSON over a custom scripting language

Almost wrote a DSL. Then remembered every dead engine that started with "first, I invented a language." Commands-as-data means the interpreter stays a switch statement, and content is diffable in git.

DECISION! Ship combat as a hook, not a system

A working battle hook you resolve with W/L keeps the narrative loop testable end-to-end today. The full card-battle system waits for Phase 2 instead of blocking everything else.

LESSONS LEARNED

/ scars, itemized
#1
Schema first, engine second.

The two "reformatted how scenes work" commits exist because I wrote the interpreter before deciding what a scene file looks like. Rewriting content hurts way more than rewriting code.

#2
A console log is a debugger you get for free.

Streaming every command and condition result to a colour-coded console turned "why did this branch fire?" from an hour of guessing into ten seconds of reading.

#3
Engines are 20% features, 80% resisting features.

The card-battle system, settings screens, and sprite animation all begged to be built first. Cutting them to Phase 2 is the only reason a playable narrative loop exists at all.
